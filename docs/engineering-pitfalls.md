# Engineering pitfalls

Patterns found while building and playtesting the phase 2 commitment/quest systems (Oct 2026) that aren't about NPC prompt wording (see `docs/npc-action-prompt-guidelines.md` for those) - these are engine/architecture/process mistakes, caught live, worth checking before repeating the same shape of bug. Check this list before adding a new generic multi-scenario action, a new per-player visibility mechanic, or a new admin reset/cleanup tool.

1. **A generic action shared across scenarios (`propose_commitment`, `accept_commitment`, `decline_commitment`) needs its own per-call role check against the specific scenario named in the arguments - granting the action name in an NPC's persona is not enough.** Confirmed live (2026-10-13): Tarin legitimately holds `propose_commitment`/`accept_commitment` for his own `discrepancy_report` scenario. With no role check, his model could also call them for the unrelated `deliver_parcel` scenario - which the engine happily applied, narrating a parcel handoff from an NPC who never actually held anything, without Mara ever being involved. `report_commitment_outcome` and `accept_handoff` already checked the calling `npc_id` against the scenario; `propose`/`accept`/`decline` didn't, purely because no scenario had needed more than one NPC with those actions granted until two scenarios shared an NPC. Fixed with `_require_proposer_role` in `world/actions.py`. When adding any new generic action usable across more than one scenario, assume it needs this check from the start rather than waiting to notice the gap.

2. **Evennia's superuser bypass silently defeats a custom per-player `view`/`search` lock, and the sole developer's own account is almost always the superuser doing the actual testing.** Confirmed live (2026-10-13): `world/build_quest_props.py`'s discoverability object used a `view`/`search` lock function (`server/conf/lockfuncs.py`'s `commitment_hint_visible`) that returned the correct value - but `access()` bypasses locks for superusers by default (`no_superuser_bypass=False`), so the object stayed visible and `look`-able regardless. The lock function being right didn't mean the mechanic worked; it needed `typeclasses.objects.CommitmentHintObject` to explicitly force `no_superuser_bypass=True` for `view`/`search` specifically. Any future narrative-visibility-via-lock mechanic needs this from the start, or it will appear broken to the one account actually testing it even though it's correct. (The alternative is `@quell`-ing before testing and un-quelling before using Builder-only commands - a valid option, just one that has to be remembered every time rather than being structurally guaranteed.)

3. **An admin reset/cleanup tool must scan the player's actual stored data for what to clear, not just the currently-authored config.** Confirmed live (2026-10-13): `resetcommitment` looped over `SCENARIOS`' current keys. Renaming a commitment type (`deliver_parcel_to_tarin`/`deposit_parcel_with_civic_office` → `deliver_parcel`, see the parcel redesign) orphaned a player's existing data under the old name - `resetcommitment` literally couldn't see it any more, because it only knew about currently-authored types. Fixed with `known_commitment_types_for()`, which unions `SCENARIOS` with whatever's actually present in the player's own data. Any reset/cleanup command needs to be robust to its own target renaming or removing the thing being reset, not just to the player's state being stale.
    - **The same applies to stores added later, not just renamed config.** Confirmed 2026-10-18: `forget` cleared a hand-kept list of an NPC's per-player `ndb` stores (`conversations`, `conversation_ids`, `turn_counters`). It missed two added afterwards: the duplicate-line gate (`last_player_message`), which could block a player's "Sure." after a reset with "You already just said that", and `world/overheard.py`'s notes. It also only ever cleared the caller's own history, so a second test character couldn't be reset at all. `commands/admin.py`'s `_forget_player` now scans every `ndb` store for the player's dbref, and `forget <npc> = <player>` targets someone else. When adding a per-player store anywhere, ask which reset tool should clear it, and prefer a reset that finds the player's entries over one that lists stores by name.

4. **An object created by one validated action and left stranded by a reset (or an orphaned commitment_type) needs its own explicit cleanup - clearing the commitment record doesn't touch the physical object.** Confirmed live (2026-10-13, same incident as #3): `resetcommitment` cleared the stale commitment bookkeeping, but the real `Parcel` object the player was still carrying - locked against get/drop/give by design - had nothing left pointing to it and no way to ever be removed again. Fixed with `cleanup_stray_parcels()`, called from the reset command. If a scenario's accept step creates a real game object, its reset path needs to independently find and remove any instance no longer tied to a currently-open commitment, not assume clearing the commitment record is enough.

5. **A reaction-triggering turn (one player message, two real model calls) must log both calls, not fold them into one log entry.** Confirmed live (2026-10-13): when a tool call triggers a follow-up "react to what you did" completion (`commands/say.py`'s `_handle_action_reaction`), the original turn's own text - what the player actually saw first - was never logged at all; only the reaction's text landed in `npc_response`, under the *original* turn's `tool_calls`. That's a real data-loss bug for exactly the logging this project exists to curate (design-bible 14.7), and it directly caused a debugging session to draw the wrong conclusion from the log. Fixed by adding `initial_response` to `conversation_log.py`'s schema. Any future multi-call turn pattern needs the same check: does every real model call actually land in the log, distinguishably?

6. **An object a validated action creates should get a real description, not just a bare key.** Confirmed live (2026-10-13): the real `Parcel` object created on accepting the parcel errand had no `desc` set, so it displayed nothing once a player actually held and looked at it - even though the discoverable room-prop version of "the same" object had a full description. Fixed by setting `parcel.db.desc` in `_create_parcel_for`, reusing the same information the room prop gives rather than inventing a second copy to maintain. When a validated action instantiates a new object, give it the description a player would expect from having already seen (or been told about) it narratively, not just enough to make the mechanic function.

7. **Clean up every object created by a live-verification `evennia shell` script, even a quick spot-check - it persists in the real game world, not a sandbox.** Confirmed live (2026-10-13): several ad hoc verification scripts run against the dev DB during this session created throwaway `Character` objects without deleting them afterward, leaving stray NPCs sitting in a real room until the project owner noticed and asked about them. Every such script needs its created objects wrapped in `try`/`finally: obj.delete()` (the pattern `world/npc_eval.py` already uses), with no exceptions for "just checking something quickly."

8. **A FORCE_REACTION_ACTIONS turn's first-pass dialogue must never actually reach the player - only its logging (#5 above) was fixed, not its display.** Confirmed live (2026-10-14, phase 3 "unverified notice" scenario): `commands/say.py`'s `_handle_llm_reply` called `_render_reply_segments` on the model's first completion's text *unconditionally*, before `validate_and_apply` ran and before checking whether this turn needed a corrective follow-up reaction. For an ordinary action this is fine - the text is right either way. But `FORCE_REACTION_ACTIONS` exists specifically for actions with a real rejectable precondition, where the model's first-pass text is exactly the text most likely to be wrong (claiming a success the engine is about to deny) - that set's own comment already says the reaction's text is meant to be "the final thing the player reads." Showing the first-pass text anyway, then showing the reaction's correction on top of it, surfaced as the model visibly announcing something and then backtracking mid-conversation (Tarin blurting out a notice detail on a plain "how's work?" before recanting once `propose_commitment` was actually rejected for an unmet prerequisite). The existing tests for this exact mechanism (`test_reaction_turn_logs_both_the_original_and_reaction_text` and friends) only ever asserted what got *logged*, never what got *displayed* (`self.messages`) - so 426/426 green tests had nothing to say about it. Fixed by hoisting the `needs_reaction` computation above the render call and skipping it entirely when true, deferring display to `_handle_action_reaction`'s own render of the corrected text. Any test written for a FORCE_REACTION_ACTIONS-style mechanism needs an assertion against the player-visible message stream, not just the log record - logging-only coverage of a mechanism whose whole point is controlling what the player sees will not catch a bug in what the player sees. **Narrowed 2026-10-17 (playtest-findings PF-0001):** hiding the first pass on *every* forced-reaction turn overcorrected. The follow-up call hands the model its first-pass text as its own earlier turn, so it writes the reaction as a continuation (just the route, just the offer), and with the first pass hidden, real answers vanished (Veska's "what do you do?", Daven's suggestions). Now the first pass is hidden only when a call is rejected; when every call applies it's shown after validation, and the follow-up ends with a system note telling the model which case it's in (`FIRST_PASS_SHOWN_NOTE` / `FIRST_PASS_HIDDEN_NOTE` in `commands/say.py`). A follow-up call needs to know what the player has actually seen, or it writes for the wrong audience.

9. **Stage files by explicit path, never a whole directory, and keep every database copy covered by an ignore rule - a swept-in DB backup puts account password hashes and invite codes into history.** Confirmed 2026-10-16: `git add prospect` staged an untracked `prospect/server/evennia.db3.pre-stepC.bak`, because `.gitignore` only matched the exact name `prospect/server/evennia.db3`. It was caught by the Tools lane before anything was pushed, but by then another branch had already merged the commit, so removing it meant rebuilding both branches rather than a one-line `git rm`. The less obvious consequence: switching to a branch where the file isn't tracked **deletes it from disk**, since git removes a tracked file that the target branch doesn't have. The backup had to be restored from the commit with `git show <commit>:<path> > <path>`. `.gitignore` now covers `prospect/server/evennia.db3.*` and `prospect/server/*.bak`. Before any commit, run `git status` and read the list; if a DB copy is ever committed, restore it from the commit *before* switching branches, and don't push or merge the branch until it's rebuilt without it.

10. **Any stage of a turn that can claim an action happened must be able to make the call, or be stopped from claiming it - otherwise the NPC's words and the game state drift apart.** Confirmed live (2026-10-18, Mara's heating errand, `prompt_version` 52, PF-0011). The follow-up reaction (`commands/say.py`'s `_handle_action_reaction`) had no tools, but it's the reply where the NPC re-asks after a dropped yes, or says "here you go" after a recorded one. Three separate bugs came out of that one gap, each found in its own live run:
    - She re-asked in words, but the ask was never recorded, so every later yes was dropped and the errand stuck.
    - She said "Here's the faulty module" after an `accept_help` that came without `give_faulty_module`, and the player never got it.
    - Given the tool, she wrote it as text (`*calls give_faulty_module*`), which went out as an action line.
   Fixed by giving the reaction exactly the tool its situation needs (`REACTION_RETRIES` for a dropped answer whose question was never recorded, `REACTION_FOLLOW_ONS` for an applied step whose next step was skipped, both in `world/actions.py`). It's validated like any other call. `world/emotes.py` drops any action naming a tool. The reverse also mattered: a reaction with nothing to add (`SPOKEN_ACTIONS`: an ask whose words were already shown) read the engine's "asks Guruth to take the module" as the player's yes and said "I'm glad you're up for it", so it's now skipped. When adding a multi-call turn, list each call and ask: can this one claim the action happened, and can it make that call? Test the player's **state at the end of the whole turn**, not just which call fired or what was shown. Every test that passed today checked one of those, and none of them caught this. Each turn's log now records which tools the reaction was offered (`reaction_tools`), so this can be checked from the log alone (#5).

11. **A model call made with tools usually returns no text when it makes a call - this applies to every pass of a turn, not just the first.** `commands/say.py`'s module docstring already says this for the first reply, and it came back the first time the reaction pass got a tool (2026-10-18): replaying the live prompt, the reaction made the call 8/8 with empty text every time, which would have left the player with only an engine line. Wherever a call is offered tools, expect to need a separate text-only call to put it into words (`_handle_action_reaction` now makes one when its reaction only made a call).
