# NPC action prompt guidelines

Patterns found while tuning the `## Actions` section of each NPC persona file and the tool-calling rules in `content/npc-shared-rules.md`, during phase-1 and phase-2A playtesting (Oct 2026) across three different models (local Ollama Qwen3, `qwen/qwen3.6-35b-a3b`/`:exacto` via OpenRouter, and `openai/gpt-4.1-mini` via OpenRouter). These are prompt-wording pitfalls, not setting content — expect them to recur with every new action, regardless of which model is behind it. Check this list before writing a new action's wording, and before changing an existing one.

Scope note: this covers how to phrase the *mechanics* of calling an action (when to call it, what the engine does and doesn't check, how to react to the result). It has nothing to do with an NPC's personality, voice, or lore — that content is authored by the project owner, per CLAUDE.md.

1. **State explicitly that the result doesn't exist until the engine confirms it, and that the engine's confirmation overrides the model's own assumption.** Without this, the model narrates the action in prose, skips the actual tool call, and then insists it already happened when corrected (observed on both `serve_drink` and `hand_over_item` before this wording was added).

2. **Never add a judgment-gate clause in the persona that the validator itself doesn't check.** `hand_over_item`'s wording once said "when there's a sensible reason," but `world/actions.py`'s `_validate_hand_over_item` only checks item type and stock — it never weighs reasonableness. That mismatch alone was enough to make the model hesitate and never call the tool. Before writing a new action's persona paragraph, read the actual validator and describe exactly what it checks, no more, no less.

3. **Cover slangy or indirect player phrasing with concrete examples; don't assume the model generalizes.** "Cup of joe" failed to trigger `serve_drink` where "iced coffee" worked moments earlier in the same conversation, same model. For any action keyed on free-text player requests, list a few deliberately oblique examples in the persona text and state plainly that there are no exceptions for unfamiliar phrasing.

4. **A prose-only "miss" in recent conversation history makes the model more likely to miss again on the next turn.** It pattern-matches its own recent reply shape rather than deciding fresh each turn. This isn't something to fix by shortening history (conversation depth is deliberately kept generous for future quest work) — it needs a rule in `content/npc-shared-rules.md` so every NPC and every action inherits it automatically: decide whether to call the action fresh each turn, regardless of what the last reply or two looked like.

5. **Distinguish a wording problem from a structural/pipeline problem early.** If a prompt rewrite — tried twice, with materially different phrasing — produces zero behavioral change, stop iterating on wording. One real example: an NPC kept giving a bare acknowledgment instead of the actual result after a tool call. Two different persona rewrites didn't fix it, because the actual cause was in `commands/say.py`: the follow-up "react to what the engine did" call was only triggered when the model left its text empty on the tool-call turn, and this model never left text empty for that action. The fix was a small code change (forcing the follow-up reaction for that action specifically), not more prompt tuning.

6. **Asterisks need an explicit "actions only, never emphasis" rule, and meta-vocabulary ("the engine," "the system," "a protocol," etc.) needs an explicit "you have no idea what that is" rule.** Both live in `content/npc-shared-rules.md` since every NPC needs them. The model reaches for both unprompted — markdown-style emphasis habits, and echoing the prompt's own instructional language back into character when questioned — unless told plainly not to.

7. **Give every action at least one required argument, even a meaningless one, or the model may never call it at all.** Confirmed empirically (2026-10-12, Phase 2A's `accept_help`/`give_faulty_module`/`exchange_module`/`accept_replacement`): a zero-argument tool schema was reliably skipped in favor of narrating the outcome in prose, across a fresh conversation with no history to blame and crystal-clear player wording ("Yes, I'll take it"). Giving the identical action a single required field (e.g. `confirmed: boolean`) made it fire every time, with no other change. This is a tool-calling-template quirk, not a wording problem — no amount of persona rewriting fixed the zero-argument version. When an action has nothing natural to parameterize, invent a trivial confirmation flag rather than leaving `parameters.required` empty; the validator can ignore the argument's value entirely if the real precondition lives elsewhere (e.g. engine-tracked state).

8. **`content/npc-shared-rules.md` must explicitly make quoting spoken dialogue and asterisking actions *mandatory*, not just describe the asterisk convention and assume the rest follows.** Confirmed live (2026-10-13, switch to `openai/gpt-4.1-mini`): without an explicit "every spoken word goes in quotes, every action goes in asterisks, nothing else is a valid reply shape" rule, the model sometimes wrote a physical action as bare unquoted prose instead of `*action*` markup, and sometimes quoted only part of a multi-sentence reply. `world/emotes.py`'s `parse_reply` only knows how to split out `*asterisk*` markup — anything else is treated as one dialogue blob, quotes and all, which the broadcast template then wraps in its *own* outer quotes, producing garbled nested-quote output (e.g. `X says, "X shrugs a little. "I haven't noticed..."`). Qwen-family models happened to default to full quoting/asterisking without being told; `gpt-4.1-mini` didn't. Make the convention a hard rule in the shared file rather than relying on a model's stylistic default.

9. **A model that splits an action into two steps (e.g. "I'll get it for you" + an emote, then stopping) can usually be nudged to complete both steps in the same turn — but only do this where it's actually true that nothing stands in the way.** Confirmed live (2026-10-13, Phase 2A's `accept_help` → `give_faulty_module` handoff): the model is capable of proposing multiple tool calls in one completion (already observed with `gpt-4.1-mini` elsewhere), but will still sometimes pace two causally-linked actions across two separate player turns, leaving an odd "she said she'd get it, then nothing happened until I spoke again" gap — not a bug (NPCs only get to act in response to a player message, there's no proactive follow-up), just occasionally unnatural pacing. Adding one sentence to the second action's persona wording — stating plainly that the item is always already on hand with nothing to fetch, and to call the follow-up action in the same turn unless there's an actual in-character reason to pause (and say so if so) — raised same-turn chaining from roughly 0/5 to 4/5 live trials, with zero false positives on a "just asking, haven't agreed" control case. This only works because it's physically true for this NPC that the item is always on hand; don't add this nudge for an action where a real pause (going to fetch something from elsewhere, finishing another task first) would be dishonest.

10. **A tool call can fire independently of whether the model's own generated dialogue actually reflects the commitment that call represents - wording can't always fix this, and two materially different rewrites producing zero change is the signal to stop.** Confirmed live (2026-10-13, `gpt-4.1-mini`, Phase 2A's `accept_help`): a genuinely ambiguous player line ("You need someone to take it to Tarin?" - a question *about* the NPC, not a first-person commitment from the player) triggered `accept_help` 10/10 trials, even after two substantially different persona rewrites explicitly distinguishing "they committed in first person" from "they asked a question about you." The tell that this had stopped being a wording problem: the model's own *generated reply* correctly hedged every single time ("You willing to do it?", "You up for it?") - it was parsing the ambiguity correctly in what it said, but the tool call fired in the same turn regardless, decoupled from its own text. Per pattern 5, don't keep iterating wording once two distinct rewrites produce identical behavior - diagnose it as a model limitation instead and decide whether the real-world consequence is worth a code-level fix (here: no, `resetquest` already covers recovery, and the state fed back every turn means dropped-and-ignored "accepted" states don't corrupt anything).

11. **The reverse of pattern 9 also happens: a model can *fully narrate* bringing up a topic in its own words while never calling the action that actually records it, every single time.** Confirmed live (2026-10-13, `gpt-4.1-mini`, Phase 2B's `propose_commitment`): asked a generic "how's work going?", Tarin reliably explained the shipment discrepancy in character, in detail, three turns in a row - with `tool_calls: []` every time. He wasn't failing to bring it up; he was treating "describing the problem" and "making the offer" as two separate steps, and pacing the second one to a later turn that never came (the player had no reason to ask again about something already explained). The fix was the same shape as pattern 9's, just one step earlier: add a sentence stating plainly that describing the problem *is* the offer, and to call the action in the same turn as deciding to mention it at all, not after. Went from 0/3 to 5/5 live. Caught by `world/npc_eval.py`'s reliability eval, not manual playtesting - worth running that harness after any wording change to an action that's reachable from an open-ended conversational opening, not just a direct question.

12. **Two unrelated "when do I bring this up unprompted" hooks on the *same* NPC bleed into each other if their trigger wording overlaps at all, even by accident.** Confirmed live (2026-10-13): Mara's heater need and her later-added parcel need both had "a generic 'how are you'/'anything I can help with' question is a valid opening" wording, and both independently quoted near-identical example phrases. The result wasn't one winning cleanly - it was unreliable in *both* directions (sometimes neither fired, sometimes both fired in the same reply, sometimes the tool call's argument didn't match what was actually said). Same thing recurred between Tarin's shipment-discrepancy discoverability and the unrelated parcel errand: a player mentioning "a package delivered to the wrong place" pulled him toward his own manifest problem, violating his own stated "not the opening exchange" bar, because the wording was shipment/delivery-themed on both sides. The fix both times was structural, not a wording tweak: give each hook genuinely non-overlapping trigger language, and have one explicitly cede the other's territory ("the parcel is yours to raise on a generic question, not the heater's") rather than independently describing similar-sounding conditions. Getting an NPC down to one discoverable hook doesn't make this class of bug impossible, though: **a general deferral rule ("send X questions to Y") counts as a competing hook too.** Confirmed live (2026-10-17, `gpt-4.1-mini`, Mara `prompt_version` 44): with the heating unit as her only errand, her new `## Pointing people the right way` section (send technical questions to whoever knows) captured "What's wrong with the heating?" as Tarin's territory, and she sent the player to the workshop empty-handed instead of asking them to carry the module. Any deferral or redirect section needs an explicit exception for the NPC's own errands, or it will hand the errand off to whoever the topic belongs to.

13. **Never let persona prose assert a fact that could contradict the per-player engine-state line injected separately into the same prompt - the model will believe the prose, not reconcile the two.** Confirmed live (2026-10-13): a wording fix for pattern 12 above included "this already came up with a customer once and got sorted out," intended as flavor explaining why the NPC stopped volunteering a topic. It directly contradicted the real injected state (`'not_started'` for *this* player - quest state is per-player, never shared-world, per the design doc) in the very same prompt. Result: asked a direct, unambiguous question on the topic, the model returned empty text and fired an unrelated tool call instead of answering at all, every trial. The lesson generalizes beyond this one case: any sentence describing *why* an NPC behaves a certain way must stay compatible with every value the per-turn state injection could actually supply for that scenario - if a state-independent behavioral choice needs explaining, explain the choice itself, not a status claim the engine might flatly disagree with.

14. **A missing vocabulary synonym is enough to make an otherwise-correct action trigger fail outright, not just underperform.** Confirmed live (2026-10-13): Tarin's persona and actions only ever used the word "parcel"; a player who said "package" instead got treated as talking about something else entirely (his unrelated shipment discrepancy), not as a slightly-off description of the same parcel. Pattern 3 already covers this for free-text arguments (drink slang); this is the same failure mode for topic *recognition* itself, not just an action's argument. List plausible synonyms explicitly ("parcel," "package," "box," "the thing X gave me") rather than assuming the model generalizes a single word used throughout a persona file to whatever a player actually says.

15. **Known issue, not expected to score well: `remember_fact` reliably fails to fire for a topic the NPC's own persona already has heavily-reinforced content about, even in the cleanest possible case (no prior memory, no history).** Confirmed live (2026-10-14, `gpt-4.1-mini`, Mara's `remember_fact`): a player stating "I'm Voldren too" scored 0/5 - every single trial, the model narrated an in-character reaction (often quoting or echoing her "Being called a Cave Crawler" section) and simply never called the action, while an unrelated personal fact ("I work as a dock loader") in the exact same harness scored 5/5. Two materially different, correctly-targeted wording fixes (explicitly stating that overlap with the NPC's own traits doesn't disqualify a fact, and explicitly stating that reacting to something is a separate step from remembering it, not a substitute) produced zero measurable change - per pattern 5/10, that's the signal to stop iterating on wording. This reads as the mirror case of pattern 11 (a model that fully narrates a topic while never calling the matching action) specifically triggered by a heavily-reinforced, highly-salient persona section crowding out an unrelated tool call on the same topic. No code-level consequence (a missed memory is not a state-corruption risk, just a worse conversation), so left as a known limitation rather than chased further. Worth testing with `world/npc_eval.py` before assuming it's fixed if this persona section changes again, and worth checking for the same pattern on any other NPC with a similarly emphatic, frequently-quoted persona section. **The opposite failure, fixed structurally (2026-10-17, playtest-findings PF-0004):** the model also stored things the player never said - Tarin, asked "What race are you?", stored his own species, then answered "What race am I?" with "You mentioned you're Drask too" and stored that. The schema and shared rules already forbade both, so `remember_fact` now requires `player_words`, the player's own statement copied from their latest message, and `world/npc_memory.py`'s `check_player_words` drops the call unless it's really there, in the first person, and not a question. A stored-claims action that a wording rule can't hold should check its source like this.

16. **Known issue, partially mitigated, not expected to reach zero: `serve_drink` can fire in the same turn as Mara's own drink *offer*, even though her own generated text is still asking the question ("Want a drink? Hot or cold?") rather than reporting an order.** Confirmed live (2026-10-14, `gpt-4.1-mini`): a player line that was agreement about something unrelated ("Truer words have never been spoken") - not a drink order - triggered `serve_drink` on a noticeable fraction of trials immediately after Mara offered a drink in that same reply, serving a drink nobody asked for. Direct orders and explicit acceptances ("Can I get a hot drink?", "Sure, cold one") stayed 100% reliable throughout. Three materially different wording passes (an "only call for an order that's actually theirs" framing, a "don't offer and serve in the same breath, that's a contradiction" framing, and a "asking a question means you don't know what to serve yet, so calling makes no sense" logical framing) each measurably reduced the false-fire rate but did not eliminate it, and the trend wasn't even monotonic across rewrites - matching pattern 10's signature exactly (the model's own text correctly hedges while the tool call fires anyway, decoupled from what it just said). Low real-world consequence (an extra unordered drink, no state corruption, nothing downstream depends on it), so left as a known, improved-but-not-solved limitation rather than chased to zero. If this needs tightening further, the next step is probably structural (a two-step offer/confirm split, mirroring the commitment actions' propose/accept pattern) rather than another wording pass - flag that trade-off to the project owner before spending more iterations on prose alone.

17. **Known issue, not expected to reach zero: an enum argument with no real information behind it gets filled with a guessed default (the first listed enum value) rather than triggering a clarifying question, even when the persona explicitly says to ask instead.** Confirmed live (2026-10-14, `gpt-4.1-mini`, Phase 2E's `report_parcel_delivery`): a fully vague report ("I delivered your parcel," "There you go, I took care of that parcel" - naming neither Tarin nor Veska at all) called the action with `reported_recipient="tarin"` (the schema's first enum option) 9/10 trials across a wording rewrite, usually with empty text and no clarifying question asked at all; one trial generated the correct clarifying question in words while still firing the guessed tool call in the same turn regardless - pattern 10's decoupled-text signature exactly. A rewrite making "never invent this argument, ask instead" more forceful produced no measurable change, so per pattern 5/10 this was logged rather than chased further. **Why this one was judged safe to leave as-is, unlike a case that would need a code-level fix**: the engine validates the reported value against the real authoritative fact regardless of whether the model guessed it or the player actually said it (`world/actions.py`'s `_validate_report_parcel_delivery` checks `reported_recipient` against the commitment's real `fulfilled_by_npc_id`) - a guess can only land on a correct match (same outcome as an honest report) or get rejected as a mismatch (same safe handling as any other wrong report), never corrupt state with an unearned success. The only real cost is an occasionally-skipped clarifying question, not a state-integrity risk. Before accepting this reasoning for a *different* action's enum argument, confirm that action's validator has the same independent-of-the-model authoritative check - this reasoning doesn't generalize to an argument the engine can't verify against anything.

18. **The same pattern as #17 recurred immediately on the next action with a similarly under-determined enum, and a separately diagnosed, genuinely different wording bug happened on the same NPC in the same session - worth distinguishing the two carefully, not lumping them together.** Confirmed live (2026-10-16, `gpt-4.1-mini`, Phase 3's "Unverified Notice"):
    - **The #17-shaped recurrence**: `report_notice_outcome`'s `reported_resolution` (`"verified"`/`"withdrawn"`) defaulted to the first enum value on a plain question naming neither (`"Did Veska ever get around to checking that notice?"`), roughly 4/10. Same resolution as #17: confirmed the validator independently rejects a wrong guess every time (0/8 false successes when tested against a mismatched real resolution), so this is safe to leave as a known limitation under the same reasoning #17 already established - not re-litigated, just confirmed to transfer.
    - **A real, separately-fixed wording bug, not a model limitation**: Tarin's NPC-initiated trigger for this same scenario scored 0/12 on two different neutral small-talk openers - not because of a model limitation, but because the persona's own prose contained a line explicitly telling him *not* to treat "how's it going" as an opening for this hook, directly contradicting the design intent that this hook should have a lower bar than an adjacent one on the same NPC. Removing that one sentence produced a real, measurable change (narration started appearing on a real fraction of trials) - proof it was a genuine wording bug. **The lesson: when two different hooks on the same NPC have deliberately different trigger bars, double-check that a sentence written to protect one hook's *higher* bar doesn't accidentally gate the other's *lower* one too** - the words "generic 'how's it going'" meant one thing in the context it was copied from and a different, wrong thing applied to a hook that was specifically supposed to accept it.
    - **A third issue on the same trigger, which did *not* resolve with wording and is logged as its own known limitation**: even after the fix above, the actual tool call (with the correct `commitment_type`) still mostly didn't fire - most trials produced no call at all, an empty-arguments call, or the wrong `commitment_type`, roughly 1-2/8 clean. A second attempt, raising `max_reply_tokens` on the hypothesis that this topic's longer narration was truncating the structured call, made no reliable difference either (also ~1/8). Two independently-motivated fixes with no reliable improvement is the stop-iterating signal (#5/#10) - left as a known limitation. Low real-world cost (a missed trigger just delays the offer to a later ordinary turn, not a state-integrity risk), but worth watching if a future scenario adds a *third* value to the shared `propose_commitment` action's `commitment_type` enum on an NPC that already juggles two - this may be an early sign that a shared, growing enum gets harder for the model to land correctly as more values are added, not something specific to this one scenario.

19. **Fixing a trigger's *reliability* (guideline #18 above) can create a new *pacing* problem, and the fix for that is a different shape again - not more wording about when the trigger is allowed to fire, but wording about not firing it in the exact turn right after something else just concluded.** Confirmed live (2026-10-14, `gpt-4.1-mini`, same "Unverified Notice" scenario): once #18's reliability fix made Tarin's low-bar trigger actually work, it started firing in the very same reply that also closed out the *other* errand (the discrepancy report) - the player asked an ordinary "keeping busy?" immediately after Tarin's own line confirming the report was filed, and he moved straight into the new topic with no gap, in the same breath as the thing that had just concluded. Mechanically correct (the low bar was always meant to allow this), but read as unnaturally eager pacing - two unrelated pieces of news landing in the same moment is not how a person actually talks, even if either one alone would be a perfectly natural thing to bring up. Two materially different wording attempts at an explicit pacing rule ("wait for the player's next reply before bringing this up") produced no reliable improvement (3/10, then a more forceful rewrite at 1/10 - worse, not better) - per #5/#10, left as a known, partially-mitigated limitation rather than chased further. Low real-world cost: an eagerly-timed topic change is a minor immersion wrinkle, not a state-integrity risk, since the engine-level gating on the notice itself is unaffected by when it gets mentioned. Worth checking for this same shape - a correctly-firing trigger landing in the same breath as an unrelated thing concluding - on any future NPC with two or more loosely-coupled unprompted hooks.

20. **An asterisked "action" can be syntactically correct (a present-tense verb, not emphasis) while still being the wrong *kind* of content: the model's own narrated deliberation about whether or how to respond, rather than anything a bystander could observe.** Confirmed live (2026-10-15, `gpt-4.1-mini`, Tarin's `accept_handoff`): a reply included `*waits to confirm they actually hand it over before responding*` immediately before the spoken line - guideline #6's "actions only, never emphasis" rule was followed to the letter (it reads as an action, not styling), but the content is meta-commentary on the model's own turn-taking, not something Tarin is doing. `content/npc-shared-rules.md` now has an explicit rule for this (a bystander-observability test); not yet run through `world/npc_eval.py` (no text-content scenario exists for this specific reply yet) - this is a single observed instance. Worth adding a scenario and checking the fire rate if this recurs.

21. **A live playtest miss didn't reproduce in a controlled `world/npc_eval.py` re-run (5/5), likely because the eval's bare `"offered, awaiting the player's answer"` state setup is missing something the real conversation had.** Confirmed 2026-10-15: `hunt_skitters`'s `accept_commitment` fired on "What is a skitter" live, despite wording that already explicitly rules this out (the same shape as pattern #10). The eval scenario reproducing just the state and player line scored 5/5 clean. The real conversation had Tarin's own `propose_commitment` reply immediately before it in history, which the eval setup (`propose_commitment()` called directly on the actor, no matching assistant turn in `history`) doesn't include. **Don't treat a clean eval score here as proof the live failure can't recur** - if it's seen again, the next step is adding the actual preceding conversation turn to the scenario's `history`, not assuming the fix already works because the simplified version passed.

20. **When a `FORCE_REACTION_ACTIONS` rejection's follow-up reaction needs the model to suppress an entire topic (not just avoid referencing a "previous attempt"), persona/shared-rules wording is markedly less effective than putting the instruction directly inside the engine's own rejection `reason` string - and even that isn't fully reliable, just measurably better.** Confirmed live (2026-10-15/16, `gpt-4.1-mini`, Quest 3's "one quest to dispense per NPC" gate): Tarin's `propose_commitment("discrepancy_report")` was correctly rejected by the engine (hunt_skitters outranked it), but the reaction call's own text still fully described the shipment-manifest problem in detail, every trial (0/5), reading to the player as "Tarin brought up the manifest" even though no state actually changed. Root cause of two early wording attempts' *total* failure, not just low success: (a) a sentence added to the `propose_commitment` tool schema's own `description` had zero effect because **the reaction call never passes `tools=` at all** (confirmed in `commands/say.py`) - the schema text is simply never sent to the model on that call, so no wording placed there can ever matter for a reaction; (b) a new, explicit rule added to `content/npc-shared-rules.md` (which *is* part of the system prompt on every call, including the reaction) still produced zero measurable change (0/5, same as before) - the model apparently doesn't reliably connect a generic "if an errand didn't go through, don't describe it" rule to a specific tool-result message that never says anything resembling that in its own words. What finally produced a *real*, measurable improvement (0/5 → 2/8, with the other 6 downgrading from a full detailed description to a brief, hedged, minimizing mention - "just some paperwork trouble," "nothing urgent," "not really off") was rewriting the rejection `reason` string itself (`world/commitments.py`'s `propose_commitment`) into a direct second-person instruction ("something else needs your attention first - don't mention this or describe it at all right now") instead of an internal state description naming the blocking commitment_type by its raw identifier. **Still not fully solved** - per #5/#10/#16, this is the point to stop iterating on wording rather than chase a fourth rewrite; logged as a known, partially-mitigated limitation. Low real-world cost: no state corruption (the commitment genuinely never opens), just an occasional vague, deliberately-downplayed hint that something minor is going on - a real improvement over a full false description, even though not zero. **Two transferable lessons for any future `FORCE_REACTION_ACTIONS` rejection that needs the model to suppress content, not just avoid self-reference**: check whether the reaction call even has access to wherever the wording lives before spending a pass on it (tool schemas don't reach it; the system prompt does), and prefer putting a direct instruction in the rejection `reason` itself - which the model sees embedded in the exact tool-result message it's reacting to - over a general rule placed elsewhere that it has to separately recall and apply.

**Final resolution, 2026-10-16: not left as an accepted limitation.** Checking the actual game log (not just eval samples) found the live leak was worse than the isolated trials suggested - a real multi-turn conversation showed Tarin reinforcing the false manifest claim four times and explicitly denying any connection to the skitters, compounding across the conversation's own history rather than a one-off slip. Given `discrepancy_report`/`unverified_notice` were phase 2/3 demo content, never one of the actual playtest's three quests, the project owner's call was to remove both scenarios entirely rather than ship a tutorial quest with a visible, partially-mitigated-only leak risk next to it - see CLAUDE.md's "One quest offer per NPC" and `docs/playtest-quest3-skitters-design.md`. The engine-level mechanism this guideline's fix contributed to (`_blocking_scenario_for_proposal`) stays as permanent, general infrastructure; it's the specific scenario pairing that triggered this exact wording failure that's gone.

22. **An NPC-initiated errand whose ask is text-only still needs #11's firm "describing the problem *is* the ask" rule, written for the words rather than a tool call.** Confirmed live (2026-10-17, `gpt-4.1-mini`, Mara `prompt_version` 44): the heating-unit errand has no propose step (it starts at `accept_help`, when the *player* commits), so the persona's soft "if a customer offers to help, or you decide to ask one" was the only thing behind the ask. Three heating cues in a row got sympathy and no ask; the player had to offer on their own, on the fourth try. Text with nothing pushing it trails off the same way an uncalled tool does. The soft wording dated from when the parcel held Mara's generic opener and the heating unit was deliberately kept lower-key (#18's shape): **when another hook is removed from an NPC, re-read the remaining hooks' trigger and ask wording, since a bar written to defer to the removed hook stays deferential after it's gone.** Fix requested from Lore as LR-DEV-0004.

23. **An action whose output names a place or a person gets used as a way to close a topic, not just to answer a request for it - scope its trigger to explicit requests, with examples of what doesn't count.** Confirmed live (2026-10-17, `gpt-4.1-mini`, Mara `prompt_version` 44): "What's wrong with the heating?" fired `give_directions` to the Maintenance Workshop ("Tarin works there if you want to ask him about it"); nobody had asked the way anywhere. The bullet only said to call it "the moment you've agreed to tell someone the way," which a "go see Tarin" answer technically satisfies. This is #3 in the negative direction: list the request phrasings that count ("how do I get to...", "which way is..."), and say plainly that naming who knows about something is a name, not a route. Applied to all four `give_directions` bullets.
