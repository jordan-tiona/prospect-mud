# Phase 2 prototype: commitments as a quest primitive

Status: Reviewed by the project owner and ChatGPT (2026-10-12). Phase 2A below
is approved and implemented; the generic `Commitment` system (§2-3) is kept as
future direction, not built now. See §11 for the reviewed roadmap and the
reasoning behind splitting it this way.
Depends on: `docs/prospect-constellation-design-v0.4.1.md` (setting canon), `CLAUDE.md` (hard rules, phase 1 scope).

## 1. Goal

Phase 1 proved LLM-voiced NPCs can hold natural conversation and reliably call one validated action each. Phase 2 asks a narrower, harder question: **can gameplay emerge from conversation**, rather than conversation just being a prettier way to access a quest menu?

The specific claim to test: an NPC's unmet need, raised in ordinary conversation, can become a tracked, engine-authoritative commitment — and different players, approaching that need in different ways, can reach different sensible resolutions without an author scripting each path and without the engine ever trusting the LLM's word for what happened.

This is deliberately the narrowest of the seven mechanics considered (see the design discussion that preceded this doc): it reuses the phase 1 tool-call pattern almost directly, needs no new architectural subsystem (no rumor propagation, no reputation modeling), and has a clean pass/fail exit test.

## 2. Core abstraction: the Commitment

A `Commitment` is a game object, not an LLM construct. It exists and changes state only through engine-validated tool calls — same hard-rule-1/2 pattern as `serve_drink` and `hand_over_item`.

Fields (draft, subject to engineering review):

- `commitment_id`
- `made_by` — NPC or player
- `made_to` — NPC or player
- `description` — short canonical text set by the engine at creation (not freely generated by the LLM; see §3)
- `condition` / `deadline` — optional, structured, not freeform prose
- `status` — `open`, `fulfilled`, `broken`, `renegotiated`
- `related_npcs` — which NPCs' knowledge scope includes this commitment

NPCs can only see commitments in their own `related_npcs` list, consistent with hard rule 5 (scoped knowledge).

## 3. Tool layer additions

New validated actions, following the existing pattern in `prospect/world/actions.py`:

- `propose_commitment` — NPC proposes a commitment to the player (e.g. "if you can confirm X, I'll do Y"). Engine validates the proposal is one of a small fixed set of commitment *types* the NPC is authored to offer — not arbitrary LLM-generated terms. The LLM chooses which authored proposal fits the conversation; it does not invent new ones.
- `accept_commitment` / `decline_commitment` — player or NPC responds; engine records state change.
- `report_commitment_outcome` — either party reports a result (e.g. player says they did the thing); engine checks the report against actual game state before marking `fulfilled`. If there's nothing in game state to check against yet (likely, for a first prototype), this call requires corroboration — see §6 open question.

This mirrors `serve_drink`'s stock check: the LLM never gets to narrate an outcome into existence. It can only trigger a tool call; the engine decides what actually happened.

**Important constraint carried over from phase 1's lessons:** commitment proposals must be a small, enumerated set per NPC, tied to concrete vocabulary in that NPC's persona file — not open-ended negotiation math (collateral, partial payment, debt amounts, etc.). Phase 1 showed that abstract shared rules weren't enough to stop tool-call misuse; only concrete, action-specific wording in the persona file worked. The same discipline applies here: each NPC's "needs" are a short authored list, not a generative space.

## 4. Scope cut for phase 2

**In scope:**
- One authored scenario, **two NPCs**, reusing existing phase 1 rooms/cast where possible rather than adding new content.
- One commitment type per NPC in the scenario (keep the enumerated set as small as possible for a first test).
- `propose_commitment`, `accept_commitment`/`decline_commitment`, `report_commitment_outcome`.
- Commitment state surfaced in conversation logging (§7).

**Explicitly deferred, not to be built in phase 2:**
- Rumor propagation / information spreading between NPCs.
- Reputation numbers or faction standing.
- Autonomous NPC goal-pursuit when the player isn't present.
- Open-ended negotiation (collateral, partial payment, counter-offers with free-form terms).
- Mediation between two NPCs' conflicting claims (the "civic dispute" mechanic) — interesting, but it's a second commitment-holder-per-side problem, not a first prototype.
- Any new rooms, NPCs, or lore beyond what's needed to host the one scenario.

**Which two NPCs, and what the scenario is** is a design decision, not an engineering one — left to the project owner. The design discussion's "Missing Filters" example is illustrative *only*; it is not canon and nothing from it should reach a prompt or a persona file unless and until you write it as real content.

## 5. Authoring additions needed

Each involved NPC's persona file gains:

- A short "current need" section: what the NPC wants, stated plainly, not as prose to be elaborated by the model.
- The enumerated commitment type(s) it can propose, worded concretely (same pattern as the `serve_drink`/`hand_over_item` fix).
- Which commitments it's currently aware of (its `related_npcs` scope).

Scenario-specific content (the actual need, the actual NPCs, any new object/room descriptions) stays `TODO(lore)` stub until the project owner writes it. Code and this doc should not invent any of it.

## 6. Open engineering question

`report_commitment_outcome` needs something to check the report against. In phase 1, `hand_over_item` had a real stock counter to validate against. A commitment like "convince the quartermaster to grant an extension" has no equivalent physical state to check — the "outcome" is itself a social fact.

Options to resolve before implementation (recommend discussing, not deciding now):
- The commitment's fulfillment condition is itself a second NPC's tool call (e.g. the quartermaster has to independently call `accept_commitment` or similar) — fulfillment becomes multi-NPC corroboration rather than a single unverified report. This keeps hard rule 1/2 intact without needing new game-state tracking.
- Or scope the first scenario to a commitment type that *does* have checkable game state (closer to `hand_over_item`), and defer purely social commitments to a later iteration.

Leaning toward the first option for realism, but the second is lower-risk for a first prototype. Flagging for a decision before writing the validator.

## 7. Logging additions

Commitment creation and state changes should land in the same `server/logs/conversations.jsonl` logging path used for tool calls today, so curation/debugging can see commitment lifecycle alongside the turn that caused it.

## 8. Exit test

Mirrors phase 1's qualitative exit test. Have 2-3 different approaches taken toward the same authored need (e.g. direct help, declining, a different offer) and check:

- Did each resolve to a *distinct*, sensible outcome without new code or dialogue being authored per path?
- Did the engine's commitment state stay accurate regardless of what the LLM narrated? (I.e., did fabrication in flavor text ever change what the engine *recorded* as fulfilled/broken?)
- Per the phase 1 deferral, isolated fabrication in NPC flavor text (invented place names, etc.) is tolerated and not a phase 2 blocker — that's logged as a model-capacity gap already. What phase 2 cannot tolerate is fabrication corrupting commitment *state itself* (hard rule 1/2 violation). That distinction is the actual pass/fail line.

## 9. Relationship to future conventional quests

Not in scope for phase 2 or its immediate successor, but worth stating as a design direction: a traditional scripted quest ("bring me 3 widgets") can be modeled as a `Commitment` the engine creates directly at scenario start, with no LLM negotiation step needed to originate it. It would reuse the same tracking, fulfillment-check, and recall machinery built here. This means phase 2's commitment system is infrastructure both conversational and conventional quests can share later, rather than a one-off built only for the emergent-dialogue case.

## 10. Phase 3

Not yet scoped. CLAUDE.md currently defines only the phase 1 prototype boundary; this document defines phase 2. Expanding commitments toward negotiation, rumor propagation, mediation, or NPC autonomy (the deferred mechanics from §4) is reasonable future work, but should wait until phase 2's exit test is run and reviewed, per the project owner's direction.

## 11. Reviewed scope split: "A Minor Inconvenience" (2026-10-12)

Per project owner + ChatGPT review, phase 2 is split into two steps rather than built as the generic `Commitment` system directly:

**Phase 2A (built now): a concrete, scenario-specific quest, not the generic system.** Mara Voss's café has a faulty temperature-control module in its heating unit; she can't fix it herself. Tarin Os can inspect it and swap it for a working one. The player is the intermediary. Per-player, persistent (`db`, not `ndb`) state, one of: `not_started`, `accepted`, `has_faulty_module`, `has_replacement_module`, `completed`. Four validated actions: Mara's `accept_help` (records the actual promise, separate from the physical handoff - this keeps the spirit of "commitment" from §2 without building the generic object) and `give_faulty_module`, Tarin's `exchange_module`, and Mara's `accept_replacement`. Each only fires from its required prior state (`world/actions.py`'s `_validate_quest_step`), so an out-of-order or repeated call is dropped, not fixed up.

Why concrete-first rather than the generic system directly: the `Commitment` system actually bundles several independent open questions (can an NPC recognize when to offer a commitment; can the model reliably call the right action with the right arguments; can multiple NPCs participate without contradicting authoritative state; can the engine verify fulfillment; can different conversational approaches produce sensible distinct outcomes). Answering all of them at once makes any failure hard to attribute. Phase 2A isolates the mechanics that are most proven already (reuses phase 1's exact validated-tool-call pattern) and defers the harder, more novel ones.

**Revised exit test for 2A** (supersedes §8 for this phase): this scenario has one intended solution path, so it does *not* demonstrate "different approaches reach different sensible outcomes" - that claim is explicitly deferred to 2B/Later, not treated as proven by a working fetch-quest. What 2A actually tests:
- Reliable tool-calling across the full accept -> give -> exchange -> accept chain.
- Each NPC's dialogue reflects its own true, current quest state (fed fresh every turn as engine truth, not left to conversation memory) rather than contradicting it.
- Sane behavior when players interrupt, repeat a step, ask questions, decline, or change the subject mid-quest - conversational flexibility, not mechanical branching.
- Hard rule 1/2 integrity holds: no amount of fabricated flavor text changes what state the engine actually recorded.
- All tool calls, including dropped/rejected ones, land in the conversation log (already true since phase 1 - confirmed, not new work).

**Explicit scope limits for 2A:**
- Quest state is an isolated, per-player instance, not shared-world simulation. Two different players each get their own independent `not_started -> ... -> completed` progression against the same Mara/Tarin - there is deliberately no shared "one broken heating unit" fact, and nothing here should be read as implying one. A future shared-world version is out of scope until explicitly designed.
- Tarin has no visibility into what the player told Mara, or into the `not_started`/`accepted` states at all (those are between the player and Mara). He only knows a module is routine to inspect and swap; why any particular player is bringing him one is whatever they tell him in their own conversation, per hard rule 5.

**Phase 2B (future, not built now): extract the `Commitment` primitive** from whatever actually worked in 2A - what "agreed to do what," which NPC's knowledge scope it touches, its fulfillment condition, how an outcome gets verified - once there's a working example to generalize from instead of guessing at the abstraction's shape upfront. Per §9, a scripted quest like 2A can be modeled as a `Commitment` created directly at scenario start, so nothing in 2A needs to be rebuilt for this.

**Later (further out): conversational and social commitments** - commitments that depend on another character's independent decision, alternative resolutions, negotiation, and eventually NPC-initiated activity. This is where §6's original "multi-NPC corroboration" question becomes relevant again; 2A deliberately avoided it by scoping to checkable game state instead.

## 12. Phase 2B requirements, for scenario co-design with ChatGPT (2026-10-13)

2A is complete, live, and confirmed working across repeated playtests (§11 above). This section is what 2B actually needs, for the project owner to take into scenario discussion with ChatGPT. It intentionally does not propose a scenario, NPCs, or any new lore - per §4, that's the project owner's call, not engineering's. It does carry a specific engineering recommendation, explained below, that should shape what kind of scenario would set 2B up to succeed.

### Already built and proven in 2A - directly reusable, no rework needed

- The validated-tool-call state-machine pattern (`world/actions.py`): precondition-gated actions, invalid/out-of-order calls dropped, not fixed up.
- Fresh per-player, per-turn engine-truth injection into the prompt (`quest_context_for` → `engage_npc`), so an NPC's belief can never drift from real state regardless of conversation history.
- Strict per-NPC knowledge scoping (hard rule 5) - proven with Tarin knowing nothing of Mara's side of the conversation.
- Per-player isolated state, not shared-world.
- The required-dummy-argument tool-schema rule, concrete wording-with-examples discipline, and the rest of `docs/npc-action-prompt-guidelines.md`'s 10 patterns - all of this generalizes directly to any new action.
- Admin `resetquest`-style recovery and conversation logging of every call (including dropped ones).

### What 2B needs to build: a generalized `Commitment` primitive

Per §2-3 (still valid, written before 2A): a `Commitment` becomes a real engine object - who made it, who it's to, an engine-set (not freely-generated) description, optional structured condition, a status (`open`/`fulfilled`/`broken`), and which NPCs' knowledge scope includes it. Three generic actions, following 2A's exact pattern: `propose_commitment` (an NPC offers one of its own small authored set - never an invented term), `accept_commitment`/`decline_commitment`, and `report_commitment_outcome`.

### The open engineering question from §6, now with a recommendation

§6 asked how `report_commitment_outcome` gets verified when there's no physical state to check against (unlike 2A's module hand-off, which always had real state). Live testing during 2A surfaced a relevant, concrete data point: when `accept_help`'s trigger depended on the model correctly judging an ambiguous player line, it false-positived 10/10 trials, and two substantially different wording rewrites didn't change that - the model's own generated dialogue correctly hedged every time, but the tool call fired anyway, decoupled from its own text (see `docs/npc-action-prompt-guidelines.md` pattern #10). That's not a one-off; it's evidence that this model's tool-calling doesn't reliably couple to fine-grained conversational judgment calls.

**Recommendation: build 2B's corroboration as a deliberately low-bar, near-unconditional trigger**, not a model-adjudicated credibility test. Concretely: the corroborating NPC's `report_commitment_outcome`-style call should fire essentially whenever it's told the thing happened (by the player, or by whatever's authored as the trigger) - the *interesting* part should live in that NPC's in-character skepticism, dialogue, and flavor text, not in the engine's actual gate. This keeps 2B inside what's actually been proven reliable. A scenario where the corroborating NPC is meant to genuinely weigh whether to believe a claim it could be lied to about is closer to §6's harder option and the "Later" tier (§11) - worth keeping on the roadmap, but not what 2B should bet its exit test on.

### What this means for picking a scenario with ChatGPT

A good 2B scenario should have a commitment type where:
- The corroborating NPC's confirmation is plausible to grant close to unconditionally once told (a "yes, they did it" moment, not a "let me investigate whether that's true" moment).
- Scope stays to §4's original cut: one scenario, two NPCs, one commitment type, reusing existing rooms/cast where possible. The project owner raised wanting to expand the world a bit for this - that's fine and the right venue for it, just note any new NPC/room/lore is new authored content (per CLAUDE.md, not engineering's to invent) and should get the same `TODO(lore)` discipline until written.
- Rumor propagation, reputation numbers, autonomous NPC goal-pursuit, open-ended negotiation, and mediation between two NPCs' conflicting claims stay explicitly out of scope (§4), same as before.

### Exit test for 2B (draft, mirrors §11's revised version)

- Reliable tool-calling across propose → accept/decline → report chain, including the new multi-NPC corroboration step.
- Both NPCs' dialogue reflects true, current commitment state fed fresh each turn.
- Hard rule 1/2 integrity: no fabricated flavor text changes what the engine actually recorded as fulfilled.
- If the scenario supports more than one sensible resolution path (declining, an alternate offer), each resolves to a distinct, sensible outcome without new code per path - this is the one claim 2A explicitly deferred (§11) and 2B is positioned to actually demonstrate, if the chosen scenario supports it.
